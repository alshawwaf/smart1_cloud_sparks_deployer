## Overview

The Smart-1 Cloud Spark Gateway Deployer automates the onboarding of Check Point Quantum Spark
gateways to Check Point Smart-1 Cloud. From a single set of configuration files, it registers each
gateway, configures the gateway object, installs the security policy and, optionally, configures
the appliance itself.

| Capability | Description |
|---|---|
| **Bulk registration** | Registers any number of gateways in Smart-1 Cloud with only a Management API key, or through the Infinity Portal API. |
| **Object configuration** | Sets the version, operating system, Spark hardware and SIC trust settings through the Management API. |
| **Policy installation** | Waits for each gateway to establish SIC, then installs the Access Control and Threat Prevention policy. |
| **Appliance configuration** | Optionally connects each appliance to Smart-1 Cloud over its local REST API. Supports Zero Touch appliances. |
| **Version awareness** | Detects the Smart-1 Cloud management version and adapts SIC configuration to it, including R82.20. |
| **Validation and logging** | Validates all configuration files before the run and keeps a rotating DEBUG log of every run. |

### Workflow

<p align="center">
  <img src="docs/images/workflow.svg" alt="Workflow: phase 1 register and configure, phase 2 configure the appliance, phase 3 install policy" width="100%">
</p>

Policy is installed last, because a gateway accepts policy only after it has connected to
Smart-1 Cloud and established SIC. Phase 3 waits for each gateway to reach the "communicating"
SIC state and installs policy only on those gateways. Zero Touch appliances that connect within
that time are included automatically.

A gateway that fails at any step is logged and skipped, and the run continues with the remaining
gateways. The run ends with a summary of each gateway and exits with a non-zero code if any
gateway was not deployed.

## Quick Start

```bash
git clone https://github.com/alshawwaf/smart1_cloud_sparks_deployer.git
cd smart1_cloud_sparks_deployer
python -m venv .venv
```

Activate the virtual environment and install the dependencies:

| Windows | Linux |
|---|---|
| `.venv\Scripts\activate` | `source .venv/bin/activate` |

```bash
pip install -r requirements.txt
```

Create your configuration files from the templates, then fill them in as described in
[Configuration](#configuration):

| Windows | Linux |
|---|---|
| `copy config\auth_data.example.json config\auth_data.json` | `cp config/auth_data.example.json config/auth_data.json` |
| `copy config\config_data.example.json config\config_data.json` | `cp config/config_data.example.json config/config_data.json` |
| `copy config\policy_package_data.example.json config\policy_package_data.json` | `cp config/policy_package_data.example.json config/policy_package_data.json` |

Run the deployment:

```bash
python s1c_deploy_sparks_gw.py
```

The run ends with a summary of each gateway. See [Live Deployment Example](#live-deployment-example)
for the output of a real run.

To remove the gateways in `config_data.json` again, run:

```bash
python s1c_deploy_sparks_gw.py --delete
```

For each gateway, `--delete`:

1. Returns the appliance to local management, when its REST API credentials are configured:
   `set maas mode stop-using`, `fw sic_reset`, `set security-management mode locally-managed`,
   and checks the result with `show security-management`.
2. Deletes the gateway object in Smart-1 Cloud, including its membership in groups such as
   `Playblocks_Gateways`, and publishes.

A gateway that no longer exists in Smart-1 Cloud is skipped, so `--delete` can be run again
safely. After `--delete`, the appliance can be deployed again from scratch.

### Requirements

- A Check Point Smart-1 Cloud tenant.
- A Management API key, created in the Smart-1 Cloud application.
- Optional: Infinity Portal API credentials (Client ID and Access Key). Not required on Smart-1
  Cloud R82.20 and later. See [Gateway Registration](#gateway-registration).
- Python 3.9 or later on Windows or Linux.
- For phase 2 (optional, not used with Zero Touch):
  - Network access to the appliance local REST API, by default on port `4434`.
  - The REST API enabled on the appliance. It is off by default. Enable it in Gaia Clish with
    `set rest-api mode on`.

> [!WARNING]
> The deployer installs the policy package exactly as it is published. Before you run it, make
> sure the policy allows the management access you need to the appliances, for example HTTPS and
> SSH from your administration network. A cleanup rule that drops all traffic locks you out of
> the appliance local interfaces as soon as the policy is installed.

## Version Compatibility

The deployer detects the Smart-1 Cloud management version at run time and adapts the SIC
configuration to it. No configuration change is required when Smart-1 Cloud is upgraded. The
detected version is shown for each gateway:

```text
INFO - Connected to Management API version 2.1
```

### Smart-1 Cloud Management

| Smart-1 Cloud | Management API | SIC configuration |
|:---:|:---:|---|
| **R82.20** | 2.1 | One-time password set after the object is converted to a Spark gateway, with `trust-settings.initiation-phase` set to `when_gateway_connects`. |
| **R82.10** | 2.0.1 | One-time password set after the object is converted to a Spark gateway. |
| **R82** | 2.0 | One-time password set after the object is converted to a Spark gateway. |

> [!IMPORTANT]
> **Smart-1 Cloud R82.20 requires the current version of the deployer.**
> R82.20 added the `trust-method` and `trust-settings` parameters to `set-simple-gateway`. When a
> one-time password is set on an object that is not yet a Spark gateway, the management server
> pushes the SIC certificate immediately. Spark appliances behind Smart-1 Cloud cannot be reached
> in this way, so earlier versions of the deployer fail at the SIC step.

### Spark Gateway Firmware

| Firmware on the appliance | Smart-1 Cloud R82.20 | `version` in `config_data.json` |
|:---:|:---:|:---:|
| **R82.00.X** | Supported | `R82` |
| **R81.10.X** | Supported | `R81.10` |
| R80.20.X and earlier | Not supported | Upgrade the appliance first |

> [!WARNING]
> Rugged 1200R appliances are not supported by Smart-1 Cloud R82.20.

> [!TIP]
> To list the versions and hardware models that your tenant accepts, run the Management API
> command `show-gateway-capabilities` with `{"platform": "smb"}`, for example from the
> SmartConsole command line.

### Gateway Registration

Each gateway is registered in Smart-1 Cloud before it is configured. The deployer chooses the
method from `auth_data.json`:

| Method | When it is used | How it works |
|---|---|---|
| **Management API** (recommended) | `client_id`, `access_key` and `portal_url` are not set | Creates the gateway object with an IP address generated by Smart-1 Cloud (`add-simple-gateway` with `auto-generate-ip`) and issues a cloud token (`set-trust` with `trust-method: cloud_token`). Requires Management API 2.1 (R82.20). |
| **Infinity Portal API** | `client_id`, `access_key` and `portal_url` are set | Registers the gateway through `POST /app/maas/api/v1/gateways` and uses the returned token. |

In both cases, the appliance joins Smart-1 Cloud with `connect maas auth-token <token>`.

## Configuration

The deployer reads three JSON files from the `config` directory. The repository contains a
template for each file. Your own files are excluded by `.gitignore`, so credentials are never
committed.

```text
config/
├── auth_data.example.json             Template: Smart-1 Cloud credentials
├── config_data.example.json           Template: one entry for each gateway
├── policy_package_data.example.json   Template: policy package and timeouts
├── auth_data.json                     Your file (not tracked)
├── config_data.json                   Your file (not tracked)
└── policy_package_data.json           Your file (not tracked)
```

> [!NOTE]
> JSON does not support comments. Each file must contain only the keys described below.

> [!IMPORTANT]
> **Upgrading from an earlier version:** the configuration files were previously tracked in the
> repository and are now excluded. Copy your `config` folder to a safe location before you run
> `git pull`, then copy your three files back into `config/`. If `git pull` reports local changes
> to the configuration files, run `git checkout -- config` after the backup and pull again.

### `config/auth_data.json`

```json
{
    "instance": "your-instance",
    "context": "your-context-uuid",
    "api_key": "your-management-api-key"
}
```

| Key | Required | Description |
|---|:---:|---|
| `instance` | Yes | Smart-1 Cloud instance name, taken from the Management API URL `https://<instance>.maas.checkpoint.com/<context>/web_api`. |
| `context` | Yes | Smart-1 Cloud context ID, taken from the same URL. |
| `api_key` | Yes | Management API key created in the Smart-1 Cloud application. |
| `client_id` | No | Infinity Portal API Client ID. Set with `access_key` and `portal_url` to register gateways through the Infinity Portal API. |
| `access_key` | No | Infinity Portal API Access Key. |
| `portal_url` | No | Infinity Portal API gateway for your region, for example `https://cloudinfra-gw-us.portal.checkpoint.com`. |

### `config/config_data.json`

```json
[
    {
        "gw_name": "sparks1",
        "version": "R81.10",
        "hardware": "1575/1595",
        "net_type": "Wireless",
        "sic_key": "your-sic-key",
        "gateway_ip": "203.0.113.171:4434",
        "gateway_username": "admin",
        "gateway_password": "your-appliance-password"
    },
    {
        "gw_name": "sparks2",
        "version": "R82",
        "hardware": "1800",
        "net_type": "Wireless",
        "sic_key": "your-sic-key"
    }
]
```

| Key | Required | Description |
|---|:---:|---|
| `gw_name` | Yes | Gateway name, used for the Smart-1 Cloud registration and the gateway object. |
| `version` | Yes | Firmware family of the appliance. See [Spark Gateway Firmware](#spark-gateway-firmware). |
| `hardware` | Yes | Spark appliance model family as shown in SmartConsole, for example `1575/1595` or `1800`. |
| `net_type` | Yes | Appliance variant, for example `Wired` or `Wireless`. |
| `sic_key` | Yes | One-time password used to establish SIC. |
| `gateway_ip` | No | Address and port of the appliance local REST API, for example `203.0.113.171:4434`. |
| `gateway_username` | No | Administrator user name on the appliance. |
| `gateway_password` | No | Administrator password on the appliance. |
| `application_control` | No | Enable the Application Control blade. Default `false`. |
| `url_filtering` | No | Enable the URL Filtering blade. Default `false`. |

> [!NOTE]
> In tenants that use Playblocks, Smart-1 Cloud adds new gateways to the `Playblocks_Gateways`
> group shortly after they are deployed. The Quarantine Policy rules for that group require
> Application Control and URL Filtering. Set both to `true` for those gateways, otherwise later
> policy installations fail with *"Rule 2 contains applications ... that require the 'Application
> Control' or the 'URL Filtering' blades"*.

To have the deployer configure the appliance in phase 2, provide all three of `gateway_ip`,
`gateway_username` and `gateway_password`. Omit them for appliances onboarded with Zero Touch.

### `config/policy_package_data.json`

```json
{
    "policy_package": "Standard",
    "install_delay": 30,
    "sic_timeout": 600
}
```

| Key | Required | Description |
|---|:---:|---|
| `policy_package` | Yes | Name of the policy package to install on the gateways. |
| `sic_timeout` | No | Seconds to wait for gateways to establish SIC before policy installation. Default `600`. Increase it for Zero Touch appliances that connect later. |
| `install_delay` | No | Reserved. Not used by the current version of the deployer. |

## Logging

| Output | Level | Content |
|---|:---:|---|
| Console | INFO | Progress of each phase and gateway. |
| `logs/s1c_deploy_sparks_gw.log` | DEBUG | Full details, including API responses. Rotated at 5 MB, with 3 backups. |

MaaS tokens, SIC one-time passwords and appliance passwords are replaced with `********` in the
console and in the log file.

**Resilience**

- Infinity Portal API requests are retried up to 3 times.
- All configuration files are validated before the deployment starts.
- Clish output from the appliance is checked, so a rejected command fails that gateway instead of
  being reported as successful.
- SIC is confirmed with `test-sic-status`, which actively tests the connection.
- After registration, the deployer waits up to 3 minutes for Smart-1 Cloud to create the gateway
  object.
- Every HTTP request has a 60-second timeout, and publish and policy installation tasks have a
  30-minute limit, so a stalled connection cannot stop the run indefinitely.
- Each phase opens and closes its own Management API session.

## Troubleshooting

| Symptom | Cause | Resolution |
|---|---|---|
| SIC errors on `set-simple-gateway`, or the gateway does not reach the "communicating" state, after the upgrade to R82.20 | Earlier versions of the deployer set the one-time password before the object was a Spark gateway | Update to the current version and confirm that the log shows `Management API version 2.1`. |
| `Policy installation failed` with a session error | Earlier versions of the deployer used a closed Management API session | Update to the current version. |
| `SIC not established with ... skipping policy installation` | The appliance did not connect to Smart-1 Cloud within `sic_timeout` | Check the appliance connectivity and the phase 2 log entries. For Zero Touch appliances, increase `sic_timeout`, or install policy from SmartConsole once the gateway connects. |
| `Config file ... not found` | The configuration file has not been created | Copy the matching `.example.json` template in `config/` and fill in your values. |
| `REST API on this appliance is off` | The appliance local REST API is disabled (default) | On the appliance, run `set rest-api mode on` in Gaia Clish. |
| `Command '...' failed: ...` in phase 2 | The appliance rejected a Clish command. The message contains the appliance output. | For `A trusted communication certificate already exists` or `You must reinitialize trusted communications`, the appliance has SIC from an earlier connection. Run `python s1c_deploy_sparks_gw.py --delete`, then deploy again. |
| `Security Gateway and Security Management policy versions are incompatible` | The policy was unloaded or changed locally on the appliance after an installation, so the accelerated policy installation no longer matches | Run `--delete` and deploy again, or disable Accelerated Install Policy for the gateway in SmartConsole (sk168055). |
| Access to the appliance is lost after policy installation, and the logs show `WebUI/SSH access attempt from unallowed source` | Earlier versions of the deployer left the gateway object with `per interface` topology and no interfaces | Update to the current version, which sets `global and automatic` topology for Spark gateways. For an existing gateway, set the topology to `global and automatic` in SmartConsole and install policy. |
| Access to the appliance is lost after policy installation, and the logs show a policy rule | The installed policy drops management traffic | Unload the policy from the appliance console, allow management access in the policy, publish, and redeploy. |
| Policy installation fails with `... require the 'Application Control' or the 'URL Filtering' blades` | The gateway was added to a group whose rules need those blades, such as `Playblocks_Gateways` | Set `application_control` and `url_filtering` to `true` for the gateway and redeploy, or enable the blades in SmartConsole. |
| `Gateway object ... not created yet` repeats and then fails | Smart-1 Cloud did not create the gateway object within 3 minutes | Confirm that the gateway is listed in the Smart-1 Cloud application in the Infinity Portal, then run the deployer again. |
| `Management server upgrade in progress` warning | Smart-1 Cloud is running a background upgrade | Wait for the upgrade to complete, then run the deployment. |
| The gateway is rejected or is not listed | Firmware earlier than R81.10.X, or a Rugged 1200R appliance | See [Version Compatibility](#version-compatibility). |

For full details of a run, see `logs/s1c_deploy_sparks_gw.log`.

## Security

> [!CAUTION]
> The configuration files contain credentials. They are excluded by `.gitignore`; do not force-add
> them to version control.

- Secrets are masked in the console and the log file. Treat the log file as sensitive anyway,
  because it contains API responses.
- The local REST API client does not verify the appliance certificate. Run phase 2 only on
  trusted management networks.
- Use a dedicated Management API key for the deployer and revoke it when it is no longer needed.

## Changelog

### November 2026: Spark topology fix and `--delete`

Verified with repeated deploy and delete cycles against the lab.

- Spark gateway objects get `interfaces-topology-settings: global and automatic`. Before, they kept
  `per interface` topology with no interfaces. Policy installation then warned about missing
  topology, and the appliance dropped local WebUI and SSH access ("access attempt from unallowed
  source") after every policy installation.
- New `--delete` mode: returns each appliance to local management and deletes its gateway object.
- New optional `application_control` and `url_filtering` settings for each gateway, for groups
  such as `Playblocks_Gateways` whose rules need those blades.

### November 2026: Lab-verified, registration without Infinity Portal keys

Verified end to end against Smart-1 Cloud (Management API 2.1) and a Quantum Spark R81.10.17
appliance.

- Gateways can be registered with only a Management API key (`add-simple-gateway` with
  `auto-generate-ip`, then `set-trust` with `cloud_token`). The Infinity Portal API credentials are
  now optional.
- SIC is confirmed with `test-sic-status`. The `sic-state` field of the gateway object stays
  `waiting_for_first_connection` after the appliance pulls its certificate, so it cannot be used.
- `connect security-management ... use-one-time-password true` was removed from appliance
  configuration. After `fetch certificate` it always fails with "You must reinitialize trusted
  communications", and the MaaS connection and certificate pull already complete the setup.
- Clish output is checked for errors, so a rejected appliance command is reported as a failure.

### November 2026: Deployment order and security

- Policy is now installed last. The appliance is configured first, then the deployer waits for
  each gateway to establish SIC (`sic_timeout`) and installs policy only on those gateways.
  Previously, policy installation ran before the appliance was connected and stopped the run
  when it failed.
- A failure no longer stops the run. Each gateway is reported in a summary, and the deployer exits
  with a non-zero code if any gateway was not deployed.
- The `fw fetch` command was removed from appliance configuration, because policy is installed
  from the management server.
- MaaS tokens, SIC one-time passwords and appliance passwords are masked in the console and the
  log file.
- All HTTP requests have a timeout, and publish and policy installation tasks have a time limit.
- The configuration files are no longer tracked. The repository now contains `.example.json`
  templates. See the upgrade note in [Configuration](#configuration).

### November 2026: Smart-1 Cloud R82.20 support

- SIC is configured after the gateway object is converted to a Spark gateway. On R82.20
  (Management API 2.1), the deployer also sets `trust-settings.initiation-phase` to
  `when_gateway_connects`, so the appliance pulls its certificate.
- Policy installation opens its own Management API session, and the logout request is sent
  correctly.
- The deployer waits for Smart-1 Cloud to create the gateway object instead of relying only on a
  fixed delay.
- The management SIC name is parsed regardless of field order or case.
- Policy installation is skipped when no gateway was configured.
- A task that partially succeeds is reported as a failure.
- Fixed `delete_gateway()` in `utils/smart1_cloud_api.py`.
- Console and log messages no longer contain emojis.
